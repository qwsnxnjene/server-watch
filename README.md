# Server Watch

HTTP-сервис для мониторинга системных метрик Linux.

Сервис собирает CPU, RAM и Disk metrics, сохраняет историю в SQLite, отслеживает состояния алертов и предоставляет HTTP API и Prometheus metrics.

На этапе 4 в проект добавлены:

* Redis;
* Redis cache для последних метрик;
* Redis storage для состояния алертов;
* fallback на in-memory состояние при недоступности Redis;
* динамическое изменение конфигурации через HTTP API;
* очередь уведомлений в Redis;
* отправка уведомлений во внешний HTTP webhook;
* уведомления о создании и разрешении алертов;
* retry для временных ошибок внешнего webhook.

Основные компоненты:

```text

                    │   HTTP Handlers  │
                    └────────┬─────────┘
                             │
                             ▼
                    ┌──────────────────┐
                    │     System       │
                    │  orchestration   │
                    └───────┬──────────┘
                            │
              ┌─────────────┼─────────────┐
              ▼             ▼             ▼
          ┌───────┐    ┌─────────┐   ┌─────────┐
          │SQLite │    │ Redis   │   │Prometheus│
          └───────┘    └─────────┘   └─────────┘
                            │
                            ▼
                    ┌──────────────────┐
                    │ Notification     │
                    │ Queue (Redis)    │
                    └────────┬─────────┘
                             │
                             ▼
                    ┌──────────────────┐
```

`System` отвечает за бизнес-логику и координацию компонентов.

Инфраструктурные детали находятся за интерфейсами:

* repository — работа с SQLite;
* alert state store — хранение состояния алертов;
* cache — кэш последних метрик;
* notification queue — очередь уведомлений;
* sender — доставка уведомлений.

# Redis

Redis используется для нескольких задач.

## Cache последних метрик

Последние собранные метрики сохраняются в Redis с TTL.

Это позволяет получать актуальные значения без обращения к SQLite.

Примерная структура ключей:

```text
server-watch:metrics:cpu
server-watch:metrics:memory
server-watch:metrics:disk
server-watch:metrics:timestamp
```

TTL кэша — 30 секунд.

SQLite при этом остаётся основным хранилищем истории.

---

## Состояние алертов

Redis также используется для хранения текущего состояния алертов.

Для изменения состояния используется атомарная Redis Lua-операция.

Это позволяет избежать ситуации, когда несколько операций изменения состояния выполняются частично.

Состояние алерта содержит информацию о:

* количестве последовательных нарушений;
* количестве последовательных нормальных значений;
* активен ли алерт.

---

## Fallback при недоступности Redis

Redis не является единственной точкой отказа для состояния алертов.

При недоступности Redis сервис переключается на in-memory storage:

```text
              Redis
                │
          доступен? ───── yes ───► Redis state
                │
                no
                │
                ▼
        In-memory state
```

После восстановления Redis состояние синхронизируется обратно.

Fallback предназначен для того, чтобы временная недоступность Redis не останавливала основную работу сервиса.

# Динамическая конфигурация

Конфигурация загружается из `config.yaml`.

Основные параметры:

```yaml
cpu_threshold: 80
mem_threshold: 90
trigger_count: 3
resolve_count: 3
slack_enabled: false
slack_url: ""
```

Также поддерживаются environment variables, которые могут переопределять значения конфигурации.

Например:

```bash
export CPU_THRESHOLD=90
export MEM_THRESHOLD=95
export TRIGGER_COUNT=5
```

---

## Изменение конфигурации через HTTP

Конфигурацию можно изменить без перезапуска приложения.

Например:

```http
PUT /config
Content-Type: application/json
```

Тело запроса:

```json
{
  "cpu_threshold": 85,
  "mem_threshold": 92,
  "trigger_count": 3,
  "resolve_count": 3
}
```

После изменения:

1. значения валидируются;
2. текущая конфигурация обновляется в памяти;
3. конфигурация сохраняется в `config.yaml`.

Таким образом, следующие циклы мониторинга используют новые значения.

### Важно

Конфигурация влияет на бизнес-логику алертов.

Например, при:

```yaml
cpu_threshold: 80
trigger_count: 3
```

алерт CPU создаётся после трёх последовательных измерений:

```text
CPU 81% → нарушено
CPU 84% → нарушено
CPU 91% → нарушено
             │
             ▼
        ALERT CREATED
```

А после трёх последовательных нормальных значений алерт разрешается:

```text
CPU 70% → normal
CPU 65% → normal
CPU 72% → normal
             │
             ▼
        ALERT RESOLVED
```

# Notification Queue

Уведомления не отправляются непосредственно из логики сбора метрик.

Вместо этого событие помещается в Redis queue.

```text
System
  │
  │ alert created/resolved
  ▼
Redis Queue
  │
  ▼
Worker
  │
  ▼
Sender
```

Это разделяет:

* определение факта возникновения алерта;
* постановку события в очередь;
* фактическую доставку уведомления.

Основная логика мониторинга не должна ждать завершения HTTP-запроса к Slack.

---

# Notification Worker

Worker постоянно читает уведомления из Redis.

Для получения сообщений используется blocking pop:

```text
BRPOP
```

Очередь работает как producer/consumer:

```text
Producer
  │
  ▼
Redis List
  │
  ▼
Consumer / Worker
```

Worker может иметь несколько `Sender`, поэтому одно уведомление может быть отправлено нескольким каналам доставки.

---

# Slack / HTTP Webhook

Для отправки используется общий HTTP sender.

Он не зависит напрямую от Slack API и работает с webhook URL.

Формат сообщения:

```json
{
  "text": "🚨 ALERT: CPU | Value: 91.20% | Threshold: 80.00%"
}
```

Для разрешения алерта:

```text
✅ RESOLVED: CPU | Value: 72.00% | Threshold: 80.00%
```

Таким образом, sender можно использовать не только для Slack, но и для других HTTP webhook-сервисов.

---

# Retry

Временные ошибки отправки повторяются.

Retry выполняется для:

* сетевых ошибок;
* HTTP 429;
* HTTP 5xx.

Обычные HTTP 4xx не повторяются, поскольку повтор запроса обычно не исправит ошибку клиента.

Количество попыток:

```text
initial attempt
      +
retry 1
      +
retry 2
```

После исчерпания попыток ошибка логируется worker'ом.

```bash

  -H "Content-Type: application/json" \
  -d '{
    "cpu_threshold": 50
  }'
```

---

# Проверка уведомлений

Для тестирования Slack/webhook необходимо:

1. включить уведомления;
2. указать webhook URL;
3. установить достаточно низкий threshold;
4. дождаться срабатывания условия алерта.

После достижения `trigger_count` сервис помещает событие в Redis queue.

Worker забирает его и отправляет через HTTP sender.

При восстановлении нормального состояния после `resolve_count` последовательных измерений создаётся событие `resolved`.

# Основные архитектурные решения

### SQLite и Redis имеют разные роли

SQLite:

* история;
* долговременное хранение;
* запросы истории.

Redis:

* быстрый cache;
* состояние активных алертов;
* очередь уведомлений;
* временные данные.

### Уведомления отделены от мониторинга

`System` не занимается HTTP-отправкой уведомлений напрямую.

Он создаёт событие и передаёт его в очередь.

Worker отвечает за доставку.

### Redis не должен останавливать сервис

Для состояния алертов существует in-memory fallback.

### Конфигурация может изменяться без перезапуска

HTTP API обновляет текущую конфигурацию и сохраняет её в файл.

### Sender является абстракцией

Worker работает с интерфейсом:

```go
type Sender interface {
    Send(notification Notification) error
}
```

Поэтому конкретный способ доставки можно заменить или добавить без изменения worker'а.

# Ограничения этапа

На этом этапе проект сознательно не решает:

* гарантированную доставку уведомлений;
* distributed locking;
* несколько экземпляров сервиса с общей координацией;
* OpenTelemetry;
* полноценную систему конфигурации;
* сложную маршрутизацию уведомлений;
* persistent message broker с гарантией доставки.

Следующий этап добавляет управление жизненным циклом приложения через `context.Context` и graceful shutdown.
