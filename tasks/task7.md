# Этап 7. Контейнеризация и подготовка к Kubernetes

## 1. Бизнес-ценность

Сервис должен быть готов к запуску в CI/CD, облачных средах и оркестрации. Это финальный этап, после которого проект можно считать production-ready с точки зрения инфраструктуры.

Этап даёт:

- воспроизводимую сборку образа;
- запуск всего стека одной командой;
- готовность к деплою в Kubernetes;
- корректную работу с секретами, конфигами и пробами.

---

# 2. Общие принципы

- Образ собирается многоступенчато, финальный образ минимален.
- Все внешние зависимости (Redis, Prometheus, Grafana) описываются в `docker-compose.yml`.
- Конфигурация передаётся через переменные окружения и/или volume с `config.yaml`.
- Секреты не попадают в образ и репозиторий.
- Все процессы корректно завершаются по `SIGTERM` (используется graceful shutdown из Этапа 5).
- Логи пишутся в `stdout` в структурированном виде (`slog` JSON).

---

# 3. Dockerfile

Образ собирается в два этапа.

## 3.1. Этап сборки (builder)

- Базовый образ: `golang:1.22` (или актуальная версия).
- Копируются `go.mod`, `go.sum`, затем исходники.
- Сборка статического бинарника с отключением CGO:
    - `CGO_ENABLED=0`
    - `GOOS=linux`
- Использование флагов линковки для уменьшения размера:
    - `-s -w`
- Бинарник собирается под имя `server-watch`.

## 3.2. Финальный этап

- Базовый образ: минимальный (Alpine или Distroless).
- Копируется только бинарник.
- Создаётся непривилегированный пользователь, от имени которого запускается сервис.
- `EXPOSE 8080`.
- `ENTRYPOINT` запускает бинарник.
- Конфигурация через переменные окружения.
- Опционально монтируется `config.yaml` через volume.

## 3.3. Требования к образу

- Размер финального образа — менее 30 МБ.
- Время сборки — разумное (без лишних слоёв).
- Образ не содержит компилятора, исходников и секретов.
- Работает без root-прав.

---

# 4. Docker Compose

Создаётся `docker-compose.yml`, поднимающий весь стек.

## 4.1. Сервисы

- `agent` — основной сервис (наш бинарник).
- `redis` — хранилище оперативного состояния и очереди.
- `prometheus` — сбор метрик.
- `grafana` — визуализация.

## 4.2. Требования

- `agent` зависит от `redis` (через `depends_on`), но не падает, если Redis недоступен (используется fallback из Этапа 4).
- Redis хранит данные в volume, чтобы очередь сохранялась между перезапусками.
- SQLite хранится в volume, чтобы история метрик и алертов не терялась.
- Prometheus конфигурируется через `prometheus.yml`, собирает метрики с `agent:8080`.
- Grafana подключается к Prometheus автоматически (через provisioning) и содержит дашборд из Этапа 6.
- Порты:
    - `agent` — 8080;
    - `prometheus` — 9090;
    - `grafana` — 3000.

## 4.3. Конфигурация

- Конфигурация агента передаётся через переменные окружения.
- Секреты (Slack webhook, пароль Redis) передаются через `.env` файл (не коммитится в Git).
- Пример `.env.example` включается в репозиторий.

---

# 5. Kubernetes (Helm-чарт)

Для деплоя в Kubernetes создаётся Helm-чарт.

## 5.1. Компоненты чарта

- `Deployment` для агента.
- `Service` (ClusterIP) для доступа к агенту.
- `ConfigMap` для не-секретной конфигурации.
- `Secret` для секретов (Slack webhook, пароль Redis).
- `PersistentVolumeClaim` для SQLite.
- Опционально: `ServiceMonitor` для Prometheus Operator.

## 5.2. Требования

- `livenessProbe` и `readinessProbe` используют `/health` (из Этапа 1).
- Пробы учитывают состояния Redis (если Redis в fallback — сервис остаётся `ready`, но с предупреждением).
- Ресурсы (requests/limits) заданы разумно (например, 100m CPU / 128Mi RAM).
- Поддерживается передача переменных окружения через `values.yaml`.
- Количество реплик — 1 по умолчанию (по причинам, описанным в Этапе 4).

## 5.3. Проверка

- Чарт успешно устанавливается в `minikube` (или `kind`).
- Pod переходит в состояние `Ready`.
- Пробы проходят.
- Логи доступны через `kubectl logs`.

---

# 6. Секреты и конфигурация

- Секреты не коммитятся в Git.
- Для локального запуска используется `.env` (в `.gitignore`).
- Для Kubernetes — `Secret` (создаётся вручную или через `helm --set`).
- Для Docker Compose — `.env`.
- В репозитории присутствует `.env.example` с перечнем переменных без значений.

Переменные окружения:

- `REDIS_ADDR`, `REDIS_PASSWORD`, `REDIS_DB`;
- `SLACK_WEBHOOK_URL`;
- `WEBHOOK_URL`;
- `LOG_LEVEL`;
- `CONFIG_PATH` (путь к `config.yaml`);
- `PPROF_ENABLED` (опционально).

---

# 7. Логирование

- Логи пишутся в `stdout` в формате JSON (`slog`).
- Уровень логирования задаётся через `LOG_LEVEL`.
- Логи не содержат секретов.
- В Kubernetes логи доступны через `kubectl logs` и могут собираться в ELK/Loki.

---

# 8. Обработка сигналов

- При получении `SIGTERM` (стандарт для Kubernetes) сервис выполняет graceful shutdown из Этапа 5.
- Kubernetes ждёт завершения в пределах `terminationGracePeriodSeconds` (по умолчанию 30 секунд, но сервис завершается быстрее).
- При превышении таймаута — принудительное завершение.

---

# 9. Нефункциональные требования

- `docker build` работает без ошибок.
- `docker-compose up` поднимает весь стек.
- Образ не превышает 30 МБ.
- Время старта контейнера — менее 2 секунд.
- Helm-чарт устанавливается в minikube без ошибок.
- Все секреты передаются через переменные окружения или Secret.
- Логи структурированы и не содержат секретов.

---

# 10. Критерии приёмки

- `docker build -t server-watch .` успешно собирает образ.
- `docker run --rm -p 8080:8080 --env-file .env server-watch` запускает сервис, `/health` возвращает 200.
- `docker-compose up` поднимает агента, Redis, Prometheus и Grafana.
- В Grafana видны метрики из Prometheus.
- `helm install server-watch ./charts/server-watch` в minikube завершается успешно.
- Pod переходит в `Ready`, пробы проходят.
- Логи доступны и структурированы.
- Секреты не попадают в образ, репозиторий и логи.
- Сервис корректно завершается по `SIGTERM`.

---

# 11. Технологический стек

- Docker;
- Docker Compose;
- Helm;
- Kubernetes (minikube или kind для проверки);
- `.env` / `Secret` для секретов;
- `log/slog` для логирования.

---

# 12. Взаимодействие с другими этапами

- **Этап 1–2**: HTTP-сервис и SQLite.
- **Этап 3**: Prometheus и Grafana.
- **Этап 4**: Redis, уведомления, конфигурация.
- **Этап 5**: graceful shutdown (используется в Kubernetes).
- **Этап 6**: метрики и бенчмарки (дашборд Grafana переносится в compose).

---

# 13. Ограничения текущей версии

- Горизонтальное масштабирование ограничено: по умолчанию одна реплика.
- SQLite не подходит для нескольких реплик (потребуется замена на PostgreSQL).
- Полноценный CI/CD (GitHub Actions, GitLab CI) не внедряется, но структура проекта готова к его добавлению.
- Service Mesh, Ingress, TLS не настраиваются.
- Мониторинг самого Kubernetes (kube-state-metrics) не подключается.
