# Этап 5. Внедрение Context и Graceful Shutdown

## 1. Бизнес-ценность

Сервис должен корректно обрабатывать таймауты, отменять долгие операции при завершении, передавать сквозные идентификаторы для трассировки и плавно останавливаться без потери данных и зависших горутин.

Это повышает надёжность сервиса до production-уровня и готовит его к работе в условиях реальной эксплуатации.

---

# 2. Общие принципы

- `context.Context` передаётся **первым аргументом** во все функции, которые выполняют I/O или могут быть отменены.
- Все внешние вызовы (SQLite, Redis, HTTP, чтение `/proc`) должны принимать контекст.
- Фоновые горутины работают до отмены корневого контекста приложения.
- При завершении сервиса корневой контекст отменяется, и все компоненты корректно останавливаются.

---

# 3. Корневой контекст приложения

При старте сервиса создаётся корневой контекст, который отменяется при получении сигналов `SIGINT` или `SIGTERM`.

Используется `signal.NotifyContext`.

Корневой контекст передаётся во все долгоживущие компоненты:

- HTTP-сервер;
- сборщик метрик;
- worker уведомлений;
- Redis health check;
- другие фоновые задачи.

При отмене контекста каждый компонент должен:

- прекратить приём новых задач;
- завершить текущие операции (в пределах таймаута);
- освободить ресурсы;
- вернуть управление.

---

# 4. Контекст в HTTP-хендлерах

Каждый хендлер использует контекст запроса через `r.Context()`.

Контекст запроса передаётся во все вызовы, которые его поддерживают:

- запросы к SQLite (`ExecContext`, `QueryContext`);
- запросы к Redis;
- HTTP-запросы к внешним сервисам (Slack, Webhook);
- чтение метрик (если операция может быть прервана).

Если клиент разрывает соединение, контекст отменяется, и обработчик должен корректно завершить работу, не выполняя лишних операций.

---

# 5. Таймауты для внешних вызовов

Для всех внешних операций устанавливаются таймауты через `context.WithTimeout`.

Минимальные требования:

| Операция | Таймаут |
|----------|---------|
| SQLite-запрос | 1 секунда |
| Redis-операция | 500 мс |
| HTTP-запрос к Slack / Webhook | 5 секунд |
| Сбор метрик (чтение `/proc`) | 2 секунды |

При превышении таймаута операция прерывается, ошибка логируется, и сервис продолжает работу.

---

# 6. Сквозной идентификатор запроса (request_id)

Для каждого входящего HTTP-запроса формируется уникальный идентификатор `request_id`.

Правила:

- если клиент передал заголовок `X-Request-ID`, использовать его значение;
- иначе сгенерировать новый UUID;
- добавить `request_id` в контекст запроса;
- добавить `request_id` во все логи, относящиеся к этому запросу;
- вернуть `X-Request-ID` в ответе клиенту.

Логирование:

- используется `slog.With("request_id", requestID)`;
- все записи в рамках обработки запроса должны содержать этот идентификатор.

Это позволяет связывать события одного запроса между собой.

---

# 7. Graceful shutdown

При получении `SIGINT` или `SIGTERM`:

1. Корневой контекст отменяется.
2. HTTP-сервер перестаёт принимать новые соединения и завершает текущие запросы в пределах таймаута (например, 10 секунд).
3. Сборщик метрик завершает текущую итерацию и останавливается.
4. Worker уведомлений завершает обработку текущего сообщения и останавливается.
5. Redis health check останавливается.
6. Соединения с SQLite и Redis закрываются.
7. Все горутины дожидаются завершения через `sync.WaitGroup`.
8. Процесс завершается с кодом 0.

Общий таймаут graceful shutdown — не более 10 секунд.

Если какой-то компонент не завершился за это время, процесс всё равно завершается (принудительно).

---

# 8. Завершение фоновых горутин

Все фоновые горутины должны:

- принимать контекст;
- проверять `ctx.Done()` в циклах;
- корректно завершаться при отмене контекста;
- не оставаться заблокированными навсегда.

Особое внимание:

- worker уведомлений использует блокирующее чтение из Redis (`BRPOP`) с ограниченным таймаутом, чтобы регулярно проверять отмену контекста;
- сборщик метрик использует `select` между тикером и `ctx.Done()`;
- health check Redis проверяет контекст между попытками.

---

# 9. Контекст в Redis

Все операции с Redis принимают контекст:

- `Get`, `Set`, `Incr`, `Expire` — через `ctx`;
- `BRPOP` — через `ctx` с таймаутом (например, 1 секунда), чтобы worker мог регулярно проверять отмену;
- health check — через `ctx` с таймаутом (например, 500 мс).

При отмене контекста операция прерывается, ошибка логируется.

---

# 10. Контекст в SQLite

Все запросы к SQLite выполняются через `ExecContext` и `QueryContext`.

Таймаут по умолчанию — 1 секунда.

При отмене контекста запрос прерывается, транзакция откатывается (если применимо).

---

# 11. Контекст в HTTP-отправителях

Все HTTP-запросы к Slack и Webhook формируются через `http.NewRequestWithContext`.

Таймаут — 5 секунд.

При отмене контекста запрос прерывается.

При ретраях каждый новый запрос создаётся с тем же контекстом (или с производным таймаутом).

Тело запроса пересоздаётся на каждой попытке (через `bytes.NewReader`), чтобы избежать проблем с повторным чтением.

---

# 12. Контекст в сборе метрик

Сборщик метрик принимает контекст и использует его для:

- прерывания чтения `/proc` (если операция долгая);
- проверки отмены в цикле;
- передачи в Redis-операции кэширования.

Таймаут одной итерации сбора — 2 секунды.

При превышении таймаута итерация пропускается, ошибка логируется.

---

# 13. Логирование

Все логи, связанные с обработкой запроса, содержат `request_id`.

При старте и остановке сервиса логируются ключевые события:

- запуск сервиса;
- подключение к Redis;
- запуск фоновых компонентов;
- получение сигнала завершения;
- остановка компонентов;
- завершение процесса.

Уровни:

- `INFO` — штатные события;
- `WARN` — временные проблемы (например, таймаут Redis);
- `ERROR` — ошибки, требующие внимания.

---

# 14. Нефункциональные требования

- Graceful shutdown завершается не более чем за 10 секунд.
- Все горутины корректно завершаются при отмене контекста.
- Нет утечек горутин.
- Все внешние вызовы имеют таймауты.
- Все логи в рамках запроса содержат `request_id`.
- При отмене контекста операции прерываются, а не продолжают работу в фоне.

---

# 15. Критерии приёмки

- `curl -H "X-Request-ID: test-123" http://localhost:8080/metrics` — в логах присутствует `request_id=test-123`.
- Если клиент не передал `X-Request-ID`, сервис генерирует его и возвращает в ответе.
- При `Ctrl+C` сервис завершается не мгновенно, а дожидается завершения текущих запросов в пределах таймаута.
- При отмене контекста фоновые горутины завершаются, в логах есть запись об остановке.
- Долгие операции (например, Redis с задержкой) прерываются по таймауту, ошибка логируется.
- Все SQLite-запросы выполняются через контекст.
- Все Redis-операции выполняются через контекст.
- HTTP-запросы к Slack/Webhook выполняются через контекст.
- После завершения сервиса не остаётся висящих горутин (проверить через `runtime.NumGoroutine()` в тестах или вручную).

# 16. Технологический стек

- `context`;
- `os/signal`;
- `sync`;
- `github.com/google/uuid` (или `crypto/rand` для генерации UUID);
- `net/http` (`http.NewRequestWithContext`, `r.Context()`);
- `log/slog`.

---

# 17. Взаимодействие с другими этапами

- **Этап 3 (Prometheus)**: экспорт метрик использует контекст для таймаутов.
- **Этап 4 (Redis, уведомления, конфигурация)**: все операции с Redis, SQLite и HTTP используют контекст.
- **Этап 6 (Контейнеризация)**: graceful shutdown и `liveness`/`readiness` пробы опираются на корректную обработку контекста.

---

# 18. Ограничения текущей версии

- Сквозная трассировка ограничена `request_id`; полноценный OpenTelemetry не внедряется.
- Таймауты фиксированы; их вынос в конфигурацию не является обязательным.
- Принудительное завершение процесса по истечении 10 секунд может привести к потере незавершённых операций (это допустимо).
