Этап 2. Бизнес‑правила и хранение истории

Бизнес‑ценность: Система автоматически выявляет аномалии, сохраняет историю метрик для анализа и позволяет получать данные за любой период.

Функциональные требования:

Добавить хранение в SQLite:

Таблица metrics: id INTEGER PRIMARY KEY, ts TIMESTAMP, cpu REAL, mem_used_mb INTEGER, mem_total_mb INTEGER, disk_used_gb INTEGER, disk_total_gb INTEGER.

Таблица alerts: id INTEGER PRIMARY KEY, ts TIMESTAMP, type TEXT, threshold REAL, value REAL, resolved BOOLEAN, resolved_ts TIMESTAMP.

Правила генерации алертов:

Алерт типа HIGH_CPU создаётся, если CPU > 80% в течение трёх последовательных измерений (15 секунд).

Алерт типа HIGH_MEM создаётся, если Memory > 90% в течение трёх последовательных измерений.

При возврате ниже порога на трёх последовательных измерениях, алерт помечается как resolved = TRUE.

Генерация алертов:

Алерт создаётся только если нет активного (unresolved) алерта данного типа.

Активным считается алерт с resolved = FALSE.

При создании алерта фиксируется текущее значение (value).

Если активный алерт уже существует, новые алерты не создаются, но можно обновлять value или last_updated (по желанию).

Алерт считается разрешённым (resolved = TRUE), когда три последовательных измерения возвращаются к нормальным значениям.

Нефункциональные требования:

Хранилище SQLite должно уметь обрабатывать не менее 1000 записей метрик в сутки.

Запросы на /history должны выполняться < 100 мс для периода до 7 дней.

Критерии приёмки:

При превышении порогов в логах появляются события, а SQLite содержит записи в таблице alerts.

После снижения нагрузки, алерты помечаются resolved.

Эндпоинт /history возвращает корректный интервал данных.
