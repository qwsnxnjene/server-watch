# Этап 4. Уведомления, динамическая конфигурация и Redis

## Бизнес-ценность
Операторы получают мгновенные оповещения в корпоративных мессенджерах о критических состояниях сервера. Пороги можно изменять без перезапуска сервиса. Redis ускоряет работу системы, добавляет надёжность и позволяет горизонтально масштабировать обработку уведомлений.

---

## Функциональные требования

### 1. Подключение и настройка Redis

- Использовать пакет `github.com/redis/go-redis/v9`.
- Настройки подключения загружать из переменных окружения:
    - `REDIS_ADDR` – адрес Redis (по умолчанию `localhost:6379`).
    - `REDIS_PASSWORD` – пароль (по умолчанию пустая строка).
    - `REDIS_DB` – номер базы (по умолчанию `0`).
- Реализовать **fallback-режим**: если Redis недоступен при старте или в процессе работы, система автоматически переключается на in-memory структуры (как на Этапе 2) и логирует ошибку. При восстановлении соединения – автоматически переключается обратно.

### 2. Использование Redis

**2.1. Кэш метрик**
- Хранить последние собранные значения метрик в Redis с TTL 30 секунд:
    - Ключи: `metric:cpu`, `metric:mem_used`, `metric:mem_total`, `metric:disk_used`, `metric:disk_total`.
- При каждом сборе обновлять значения.
- В хендлере `/metrics` (JSON и Prometheus) приоритетно читать из Redis, при ошибке – из локальной памяти (или SQLite).

**2.2. Счётчики и состояние алертов**
- Вместо глобальных переменных (`AlertState`) использовать Redis для хранения:
    - `alert:cpu:count` – счётчик последовательных превышений для CPU (int).
    - `alert:mem:count` – счётчик последовательных превышений для Memory (int).
    - `alert:cpu:active` – флаг активности алерта (1/0).
    - `alert:mem:active` – флаг активности алерта (1/0).
- Использовать атомарные операции:
    - `INCR` при превышении порога.
    - `SET 0` при снижении ниже порога.
    - `EXPIRE` (например, 60 секунд) для автоматического сброса счётчиков при длительном отсутствии данных.

**2.3. Очередь уведомлений**
- При создании или разрешении алерта добавлять сообщение в Redis List:
    - Ключ: `notifications:queue`.
    - Сообщение – JSON с полями: `type` (HIGH_CPU/HIGH_MEM), `action` (created/resolved), `value`, `threshold`, `timestamp`.
- Запустить **воркеры** (2–3 горутины), которые в цикле:
    - Выполняют `BRPOP notifications:queue 0` (блокирующее чтение).
    - Полученное сообщение отправляют в Slack (или Webhook).
    - При успехе – логируют INFO, при ошибке – ERROR и удаляют сообщение из очереди (чтобы избежать зацикливания). Допустима потеря одного уведомления в случае сбоя (учебный проект).

### 3. Уведомления

**3.1. Основной канал — Slack (обязательный)**
- Использовать **Incoming Webhook** Slack.
- URL вебхука загружается из переменной окружения `SLACK_WEBHOOK_URL`.
- При недоступности Slack (ошибка HTTP) – логировать ошибку и повторять попытку не более 2 раз (с экспоненциальной задержкой). При окончательной неудаче – логировать ERROR, но не блокировать работу.

**3.2. Дополнительный канал — Webhook (опциональный)**
- Добавить возможность отправлять уведомления на любой HTTP-эндпоинт (например, для интеграции с корпоративным мессенджером или системой тикетов).
- Настройка через переменную окружения `WEBHOOK_URL`.
- Тело запроса — JSON:
  ```json
  {
    "type": "HIGH_CPU",
    "action": "created",
    "value": 85.2,
    "threshold": 80,
    "timestamp": "2025-01-01T12:00:00Z"
  }Метод: POST, Content-Type: application/json.

**3.3. Другие каналы — по желанию (не обязательны)**

- Архитектура с интерфейсом `Notifier` позволяет легко добавить Telegram, Mattermost, Discord и другие каналы в будущем. В рамках текущего ТЗ эти каналы **исключаем**.

**3.4. Формат сообщений**

- Slack (и Webhook):
    - При создании алерта: `🚨 ALERT: {type} | Value: {value}% | Threshold: {threshold}% | Time: {timestamp}`.
    - При разрешении: `✅ RESOLVED: {type} | Value: {value}% | Threshold: {threshold}% | Time: {timestamp}`.

**3.5. Асинхронность и надёжность**

- Отправка выполняется через Redis-очередь (как в основном ТЗ).
- Воркеры читают из очереди и отправляют уведомления последовательно.
- При ошибке отправки — логировать ERROR и удалять сообщение из очереди (чтобы избежать бесконечных повторов). Допустима потеря одного уведомления в случае сбоя — это учебный проект.

### 4. Динамическая конфигурация

**4.1. Источники конфигурации**

- Файл `config.yaml` (или `config.json`) в корне проекта:

  yaml
  ```
  thresholds:
    cpu: 80
    mem: 90
  notifications:
    slack:
      enabled: true
      webhook_url: "https://hooks.slack.com/services/xxx/yyy/zzz"
    webhook:
      enabled: false
      url: "https://my-corporate-system.com/alerts"
  ```
  svgsvg
- Переменные окружения имеют приоритет над файлом (переопределяют значения).
- При отсутствии файла – используются значения по умолчанию (cpu=80, mem=90, уведомления выключены).

**4.2. Эндпоинт для изменения конфигурации**

| **МетодПутьОписаниеТело запросаОтветКоды ошибок** |           |                                         |                                                           |                                 |                                                                         |
| ------------------------------------------------- | --------- | --------------------------------------- | --------------------------------------------------------- | ------------------------------- | ----------------------------------------------------------------------- |
| `POST`                                            | `/config` | Изменить пороги и настройки уведомлений | `{"cpu":75, "mem":85, "slack_webhook_url":"https://..."}` | Обновлённая конфигурация в JSON | `200` – успех<br>`400` – неверные значения<br>`500` – ошибка сохранения |

**4.3. Валидация**

- CPU и Memory пороги: числа от 0 до 100.
- Consecutive пороги: числа, большие 0.
- Slack Webhook URL: если передан, должен быть валидным HTTP/HTTPS URL.
- При невалидных данных – возвращать 400 с описанием ошибки.

**4.4. Применение изменений**

- Обновлённая конфигурация применяется мгновенно (без перезапуска).
- Файл `config.yaml` перезаписывается новыми значениями.
- Изменения логируются (INFO).

### 5. Логирование (slog)

- Все операции с Redis логировать на уровне DEBUG (при включённом уровне).
- Отправка уведомлений:
    - Успех – INFO.
    - Ошибка – ERROR с деталями (канал, текст ошибки).
- Изменение конфигурации – INFO с новыми значениями.
- Переключение между Redis и fallback-режимом – WARN/ERROR.

---

## ⚙Нефункциональные требования

- Время отправки уведомления – не более 5 секунд после создания алерта.
- Очередь уведомлений должна быть устойчива к перезапуску (сохраняется в Redis).
- Изменение конфигурации применяется мгновенно без перезапуска сервиса.
- При недоступности Redis система продолжает работать (с логами ошибок).
- Все логи структурированные (JSON) и содержат: `level`, `time`, `msg`, `component`.

---

## Критерии приёмки

- При превышении порогов в Slack приходит сообщение с типом алерта и значением.
- При возврате к норме – сообщение о разрешении алерта.
- После `POST /config` новые пороги начинают действовать.
- Файл `config.yaml` обновляется после успешного изменения через API.
- При отключении Redis система продолжает работать (все метрики и алерты работают через in-memory).
- В логах присутствуют структурированные записи о всех ключевых событиях.
- При старте с невалидным конфигом – сервис падает с ошибкой (fail-fast).

- SQLite остаётся для долгосрочного хранения (история метрик и алертов).

## Дополнительные замечания

- Для локальной разработки Redis можно поднимать через Docker (`docker run -p 6379:6379 redis`).
- В `docker-compose.yml` (Этап 5) будет добавлен сервис Redis.
- Для тестирования уведомлений можно использовать тестовый Slack-вебхук.
- При реализации fallback-режима важно корректно обрабатывать ошибки подключения и переподключения.
- Telegram исключён из ТЗ из-за возможных блокировок в России; при желании его можно добавить как дополнительный канал, реализовав интерфейс `Notifier`.
