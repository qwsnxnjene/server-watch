# Этап 4. Уведомления, динамическая конфигурация и Redis

## 1. Бизнес-ценность

Сервис должен автоматически уведомлять операторов о критических состояниях сервера через Slack и другие HTTP webhook-каналы.

Пороговые значения и настройки уведомлений должны изменяться без перезапуска сервиса.

Redis используется как инфраструктурный слой для:

* кэширования последних метрик;
* хранения состояния алертов;
* очереди уведомлений;
* сохранения очереди между перезапусками сервиса.

При недоступности Redis основная функциональность сервиса должна сохраняться за счёт локальных in-memory механизмов.

---

# 2. Подключение и настройка Redis

Для работы с Redis используется:

`github.com/redis/go-redis/v9`

Параметры подключения загружаются из переменных окружения:

* `REDIS_ADDR` — адрес Redis, по умолчанию `localhost:6379`;
* `REDIS_PASSWORD` — пароль, по умолчанию пустая строка;
* `REDIS_DB` — номер базы Redis, по умолчанию `0`.

Redis-клиент создаётся отдельным инфраструктурным компонентом.

Сервис периодически проверяет доступность Redis.

При недоступности Redis:

* ошибка фиксируется в структурированном логе;
* сервис продолжает работу;
* компоненты, использующие Redis, переходят на предусмотренные fallback-механизмы.

После восстановления Redis сервис должен попытаться вернуться к использованию Redis.

---

# 3. Кэш системных метрик

Redis используется для хранения последних собранных системных метрик.

Кэш имеет ограниченное время жизни — **30 секунд**.

Используются ключи с общим префиксом приложения:

* `metric:cpu`;
* `metric:mem_used`;
* `metric:mem_total`;
* `metric:disk_used`;
* `metric:disk_total`;
* timestamp последнего измерения.

При каждом успешном сборе метрик значения обновляются в Redis.

Компонент кэша отвечает только за хранение и получение последних метрик и не содержит бизнес-логику алертов.

При недоступности Redis сервис продолжает использовать локальное состояние метрик.

SQLite при этом сохраняется как долговременное хранилище истории и не заменяется Redis-кэшем.

---

# 4. Состояние алертов

## 4.1. Модель состояния

Состояние каждого типа алерта включает:

* количество последовательных измерений с одинаковым условием;
* текущее условие (`HIGH` / `NORMAL`);
* признак активного алерта.

Для каждого типа алерта состояние хранится отдельно.

Минимально поддерживаются:

* `HIGH_CPU`;
* `HIGH_MEM`.

Redis используется как основное хранилище состояния.

Пример ключей:

```text
server-watch:alert:cpu:count
server-watch:alert:cpu:condition
server-watch:alert:cpu:active

server-watch:alert:mem:count
server-watch:alert:mem:condition
server-watch:alert:mem:active
```

Фактический префикс ключей определяется конфигурацией Redis-компонента.

## 4.2. Обновление состояния

При получении нового измерения:

* если значение выше порога — последовательный счётчик увеличивается;
* если значение возвращается в норму — состояние последовательности изменяется и счётчик начинается заново;
* активный алерт не создаётся повторно, если он уже существует;
* активный алерт разрешается только после достижения необходимого количества последовательных нормальных измерений.

По умолчанию:

```text
AlertTriggerCount = 3
AlertResolveCount = 3
```

Таким образом:

```text
HIGH
HIGH
HIGH → создание алерта

NORMAL
NORMAL
NORMAL → разрешение алерта
```

Пороговые значения и количество последовательных измерений являются частью динамической конфигурации сервиса.

## 4.3. Атомарность

Операции изменения состояния Redis должны выполняться атомарно там, где это необходимо для корректной работы счётчиков и состояния алертов.

Для увеличения счётчиков используется Redis `INCR`.

Для сохранения полного состояния алерта используется атомарная операция Redis, позволяющая обновить связанные значения согласованно.

---

# 5. Fallback для состояния алертов

При недоступности Redis состояние алертов переносится в in-memory хранилище.

Fallback должен поддерживать те же операции, что и Redis-хранилище состояния.

Таким образом, бизнес-логика системного слоя не зависит от конкретного backend'а.

Архитектура:

```text
System
  ↓
AlertStateBackend
  ├── Redis
  └── In-memory fallback
```

Redis является основным backend'ом.

При ошибке Redis:

```text
Redis → недоступен
        ↓
in-memory fallback
```

После восстановления Redis:

```text
in-memory
    ↓
синхронизация состояния
    ↓
Redis
```

При синхронизации актуальное in-memory состояние записывается обратно в Redis.

## 5.1. Ограничение fallback-режима

Во время работы без Redis сервис теряет распределённую консистентность.

Если одновременно запущено несколько экземпляров сервиса, каждый экземпляр будет иметь собственное in-memory состояние.

Это может привести к:

* дублированию алертов;
* пропуску алертов;
* различающимся счётчикам между экземплярами.

Для текущего учебного проекта это допустимо, поскольку основной сценарий предполагает один экземпляр сервиса.

При дальнейшем горизонтальном масштабировании Redis должен оставаться доступным как общее хранилище состояния.

---

# 6. Очередь уведомлений

Уведомления не отправляются непосредственно из логики обработки алертов.

После создания или разрешения алерта формируется объект уведомления:

```json
{
  "type": "HIGH_CPU",
  "action": "created",
  "value": 85.2,
  "threshold": 80,
  "timestamp": "2025-01-01T12:00:00Z"
}
```

Поддерживаемые действия:

* `created`;
* `resolved`.

Уведомление передаётся в очередь.

Redis используется как основная реализация очереди на основе Redis List.

Ключ очереди имеет вид:

```text
server-watch:notifications:queue
```

Фактический префикс определяется конфигурацией Redis-компонента.

## 6.1. Worker

Отдельный worker получает уведомления из очереди и передаёт их зарегистрированным отправителям.

Worker работает до отмены общего контекста приложения.

Чтение из Redis выполняется блокирующей операцией с ограниченным таймаутом, что позволяет worker'у регулярно проверять отмену контекста и корректно завершаться при shutdown.

Если очередь пуста, worker продолжает ожидание.

Если Redis временно недоступен, ошибка логируется, после чего worker продолжает работу.

## 6.2. Ошибки отправки

Ошибка отправки уведомления не должна останавливать worker и не должна блокировать сбор метрик.

После окончательной неудачи уведомление удаляется из очереди.

Для текущего учебного проекта допустима потеря отдельного уведомления при окончательной ошибке отправки.

---

# 7. Отправители уведомлений

Для отправки уведомлений используется интерфейс:

```text
Sender
```

Он позволяет подключать несколько независимых каналов доставки.

Текущая архитектура поддерживает:

* Slack;
* произвольный HTTP webhook.

Другие каналы в рамках текущего этапа не реализуются.

---

# 8. Slack

Slack является основным обязательным каналом уведомлений.

Используется Slack Incoming Webhook.

URL webhook загружается из конфигурации/переменных окружения.

Секрет webhook не должен:

* попадать в Git;
* выводиться в логи;
* включаться в текст ошибок;
* возвращаться клиенту через API конфигурации.

## 8.1. Формат сообщения

При создании алерта:

```text
🚨 ALERT: {type} | Value: {value}% | Threshold: {threshold}% | Time: {timestamp}
```

При разрешении:

```text
✅ RESOLVED: {type} | Value: {value}% | Threshold: {threshold}% | Time: {timestamp}
```

## 8.2. Повторные попытки

При временной ошибке HTTP отправка повторяется не более двух раз.

Повтор применяется для:

* ошибок сети;
* HTTP `429`;
* HTTP `5xx`.

Между попытками используется увеличивающаяся задержка.

Обычные клиентские ошибки HTTP `4xx`, кроме `429`, повторно не отправляются.

После окончательной неудачи ошибка записывается в лог, но работа сервиса продолжается.

---

# 9. HTTP Webhook

Дополнительно поддерживается отправка уведомлений на произвольный HTTP endpoint.

Webhook отправитель реализует тот же интерфейс `Sender`, что и Slack sender.

Запрос:

```text
POST {WEBHOOK_URL}
Content-Type: application/json
```

Тело:

```json
{
  "type": "HIGH_CPU",
  "action": "created",
  "value": 85.2,
  "threshold": 80,
  "timestamp": "2025-01-01T12:00:00Z"
}
```

Формат данных уведомления должен быть одинаковым для всех HTTP-каналов.

---

# 10. Динамическая конфигурация

## 10.1. Источники конфигурации

Основной файл:

```text
config.yaml
```

Конфигурация включает:

* порог CPU;
* порог памяти;
* количество последовательных измерений для создания алерта;
* количество последовательных измерений для разрешения алерта;
* настройки Slack;
* настройки HTTP webhook.

Переменные окружения имеют приоритет над значениями из YAML.

При отсутствии конфигурационного файла используются значения по умолчанию.

## 10.2. Значения по умолчанию

По умолчанию:

```text
CPU threshold = 80
Memory threshold = 90

Trigger count = 3
Resolve count = 3

Slack = disabled
Webhook = disabled
```

Redis по умолчанию:

```text
REDIS_ADDR = localhost:6379
REDIS_PASSWORD = ""
REDIS_DB = 0
```

## 10.3. Загрузка конфигурации

При запуске сервиса:

1. загружается YAML-файл;
2. применяются значения по умолчанию для отсутствующих параметров;
3. значения из переменных окружения имеют приоритет;
4. конфигурация валидируется;
5. при ошибке валидации сервис завершается с ошибкой.

Сервис использует fail-fast поведение при старте с невалидной конфигурацией.

---

# 11. Изменение конфигурации через API

Для изменения конфигурации используется:

```text
POST /config
```

Пример запроса:

```json
{
  "cpu_threshold": 75,
  "mem_threshold": 85,
  "trigger_count": 3,
  "resolve_count": 3,
  "slack_enabled": true,
  "slack_webhook_url": "https://example.com/webhook"
}
```

Поля являются частичными: переданное поле изменяется, а отсутствующее сохраняет текущее значение.

После успешной валидации новая конфигурация:

1. применяется в памяти;
2. сохраняется в YAML-файл;
3. становится доступной последующим циклам мониторинга.

Изменения не требуют перезапуска сервиса.

Если сохранение файла завершается ошибкой, ошибка возвращается клиенту согласно контракту API.

При этом поведение обновления конфигурации в памяти должно соответствовать принятой политике сервиса: изменение не должно приводить к необходимости перезапуска процесса.

---

# 12. Валидация конфигурации

Порог CPU:

```text
0 <= value <= 100
```

Порог памяти:

```text
0 <= value <= 100
```

Количество последовательных измерений:

```text
value > 0
```

URL Slack и HTTP webhook, если указаны, должны быть корректными HTTP/HTTPS URL.

Невалидная конфигурация не применяется.

При ошибке API возвращает:

```text
400 Bad Request
```

с описанием причины ошибки.

---

# 13. SQLite

SQLite продолжает использоваться как долговременное хранилище.

Redis не заменяет SQLite.

SQLite отвечает за:

* историю системных метрик;
* историю алертов;
* информацию о разрешённых алертах.

Redis отвечает за оперативные данные:

* текущий кэш метрик;
* состояние алертов;
* очередь уведомлений.

Таким образом:

```text
SQLite → долговременное хранение
Redis  → оперативное состояние и очередь
Memory → fallback при недоступности Redis
```

---

# 14. Prometheus

Экспорт Prometheus продолжает работать независимо от наличия Redis.

Текущие значения метрик должны быть доступны через Prometheus endpoint.

Redis используется как дополнительный источник оперативных данных, но недоступность Redis не должна приводить к прекращению экспорта метрик.

При невозможности получить данные из Redis используется локальное состояние сервиса.

---

# 15. Логирование

Для логирования используется `log/slog`.

Все ключевые события логируются структурированно.

Минимально должны фиксироваться:

### Redis

* ошибки подключения;
* ошибки операций;
* восстановление соединения;
* переход в fallback;
* возврат из fallback.

Подробные успешные Redis-операции могут логироваться на уровне `DEBUG`.

### Уведомления

Успешная отправка:

```text
INFO
```

Ошибка отправки:

```text
ERROR
```

В записи должны присутствовать как минимум:

* канал;
* тип алерта;
* действие;
* текст ошибки.

### Конфигурация

Изменение конфигурации:

```text
INFO
```

При этом секретные значения, включая webhook URL, не должны попадать в лог.

### Алерты

Создание и разрешение алерта:

```text
INFO
```

---

# 16. Graceful shutdown

Фоновые компоненты должны завершаться при отмене общего контекста приложения.

Это относится как минимум к:

* сборщику метрик;
* worker уведомлений;
* Redis health check;
* HTTP-серверу.

Worker не должен оставаться заблокированным на бесконечном ожидании Redis при остановке приложения.

---

# 17. Надёжность

При недоступности Redis:

* сбор метрик продолжается;
* SQLite продолжает работать;
* локальные метрики продолжают обновляться;
* состояние алертов переключается на in-memory;
* HTTP API продолжает работать;
* сервис не завершается только из-за отказа Redis.

При недоступности Slack:

* ошибка логируется;
* выполняются предусмотренные повторные попытки;
* после окончательной ошибки worker продолжает работу;
* основная бизнес-логика сервиса не блокируется.

При недоступности дополнительного HTTP webhook поведение аналогично Slack sender.

---

# 18. Нефункциональные требования

* Уведомление должно быть поставлено в очередь сразу после изменения состояния алерта.
* При штатной работе Redis уведомление должно доставляться в канал в течение нескольких секунд.
* Redis-очередь должна сохранять сообщения между перезапусками сервиса.
* Изменение конфигурации применяется без перезапуска.
* Redis является отказоустойчивым внешним компонентом только при его доступности; при сбое используется локальный fallback.
* Все ключевые события логируются через `slog`.
* Секреты не должны попадать в репозиторий и логи.
* Сервис должен корректно завершать фоновые горутины при shutdown.

---

# 19. Критерии приёмки

### Redis

* сервис подключается к Redis с параметрами из окружения;
* при недоступности Redis сервис продолжает работу;
* после восстановления Redis сервис возвращается к Redis;
* состояние alert backend синхронизируется после восстановления;
* кэш метрик имеет TTL;
* очередь уведомлений хранится в Redis.

### Алерты

* после трёх последовательных превышений создаётся алерт;
* повторное превышение не создаёт дубликат активного алерта;
* после трёх последовательных нормальных измерений активный алерт разрешается;
* при создании алерта создаётся notification `created`;
* при разрешении создаётся notification `resolved`.

### Slack

* при создании алерта приходит сообщение `ALERT`;
* при разрешении приходит сообщение `RESOLVED`;
* временные ошибки отправки повторяются;
* окончательная ошибка не останавливает сервис.

### Webhook

* HTTP sender отправляет `POST`;
* используется `Content-Type: application/json`;
* тело содержит тип, действие, значение, порог и timestamp;
* ошибка webhook не останавливает сервис.

### Конфигурация

* `POST /config` изменяет настройки без перезапуска;
* новые пороги используются следующим циклом мониторинга;
* конфигурация сохраняется в YAML;
* невалидные значения отклоняются;
* невалидный конфиг при старте приводит к завершению сервиса;
* секретные значения не возвращаются и не логируются в открытом виде.

### Хранилища

* SQLite продолжает хранить историю метрик и алертов;
* Redis используется для оперативных данных;
* при отказе Redis работает in-memory fallback.

### Завершение

* сервис корректно завершается по `SIGINT`/`SIGTERM`;
* фоновые worker'ы и health check завершаются вместе с приложением.

# 21. Ограничения текущей версии

Текущая версия проекта рассчитана прежде всего на работу одного экземпляра сервиса.

При недоступности Redis fallback на in-memory сохраняет работоспособность, но не обеспечивает распределённую консистентность между несколькими экземплярами.

Полноценная горизонтальная масштабируемость требует постоянной доступности общего Redis-хранилища и отдельного решения вопросов распределённой обработки уведомлений.
