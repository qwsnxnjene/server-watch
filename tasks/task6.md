# Этап 6. Производительность, метрики и бенчмарки

## 1. Бизнес-ценность

Сервис должен быть не только функциональным, но и измеримым. Необходимо понимать, какую нагрузку он выдерживает, где находятся узкие места и как меняется производительность при изменениях кода.

Этап даёт ответы на вопросы:

- Какой RPS выдерживает сервис?
- Какие задержки видят пользователи (P50 / P95 / P99)?
- Где находятся узкие места (БД, Redis, HTTP, сбор метрик)?
- Как изменения в коде влияют на производительность?

---

# 2. Общие принципы

- Все измерения должны быть воспроизводимыми и документированными.
- Метрики latency собираются для всех HTTP-эндпоинтов.
- Бизнес-метрики экспортируются в Prometheus.
- Нагрузочные тесты запускаются по документированной методике.
- Go-бенчмарки покрывают критичные функции.
- Результаты фиксируются в документации.

---

# 3. HTTP-метрики latency

Для каждого HTTP-эндпоинта собирается гистограмма времени обработки.

Используется `prometheus.HistogramVec` с лейблами:

- `path` — путь эндпоинта;
- `method` — HTTP-метод;
- `status` — HTTP-статус ответа.

Покрываются как минимум эндпоинты:

- `/metrics`;
- `/health`;
- `/history`;
- `/alerts`;
- `/config`.

Гистограмма должна позволять вычислять перцентили P50, P95, P99 в Prometheus.

Бакеты гистограммы подбираются с учётом ожидаемых задержек (например, от 1 мс до 5 секунд с логарифмическим шагом).

Метрика регистрируется один раз и обновляется при каждом запросе.

---

# 4. Дашборд Grafana

В Grafana добавляется дашборд, отображающий:

- RPS по каждому эндпоинту;
- P50, P95, P99 latency по каждому эндпоинту;
- количество алертов (созданных / разрешённых);
- количество уведомлений по каналам и статусам;
- размер очереди уведомлений;
- ошибки Redis и других компонентов.

Дашборд предоставляется в виде JSON-файла и автоматически подключается через provisioning.

---

# 5. Нагрузочное тестирование

Для измерения RPS и latency под нагрузкой используется один из инструментов:

- `hey`;
- `k6`;
- `vegeta`.

Инструмент выбирается по удобству; в рамках проекта достаточно одного.

Сценарии нагрузки:

- **Сценарий 1**: только `/health` — базовая проверка.
- **Сценарий 2**: `/metrics` (JSON) — работа с кэшем.
- **Сценарий 3**: `/metrics` (Prometheus) — экспорт метрик.
- **Сценарий 4**: `/history` — работа с SQLite.

Для каждого сценария фиксируются:

- длительность теста;
- количество конкурентных клиентов;
- целевой RPS (если применимо);
- полученные P50 / P95 / P99;
- максимальный устойчивый RPS.

Результаты сохраняются в документации (например, `docs/benchmarks.md`).

---

# 6. Go-бенчмарки

Для критичных функций пишутся бенчмарки с использованием `testing.B`.

Минимально покрываются:

- сбор метрик (чтение `/proc`, вычисление CPU);
- логика переходов состояния алертов (HIGH → NORMAL и обратно);
- сериализация и десериализация JSON для API;
- операции с Redis (in-memory fallback и реальный клиент, если возможно);
- запись и чтение из SQLite.

Бенчмарки запускаются командой `go test -bench=. -benchmem` в соответствующих пакетах.

Результаты фиксируются в документации и сравниваются при изменениях кода.

---

# 7. Профилирование (опционально)

Опционально подключается `net/http/pprof`.

Доступные профили:

- `/debug/pprof/profile` — CPU;
- `/debug/pprof/heap` — память;
- `/debug/pprof/goroutine` — горутины.

Профилирование используется для поиска узких мест, но не является обязательным для сдачи этапа.

Включается через переменную окружения `PPROF_ENABLED`.

По умолчанию выключено.

---

# 8. Документация

В репозитории создаётся файл `docs/benchmarks.md`, содержащий:

- описание методики нагрузочного тестирования;
- используемый инструмент и его версию;
- сценарии нагрузки;
- результаты (таблицы P50 / P95 / P99 и RPS);
- результаты Go-бенчмарков;
- выводы и обнаруженные узкие места.

Документация обновляется при значимых изменениях в коде.

---

# 9. Нефункциональные требования

- Измерения воспроизводимы: одна и та же команда даёт сравнимые результаты.
- Метрики latency не искажают работу сервиса (накладные расходы минимальны).
- Нагрузочные тесты не приводят к падению сервиса при умеренной нагрузке.
- Бенчмарки запускаются быстро (в пределах разумного времени).
- Документация позволяет повторить измерения на другой машине.

---

# 10. Критерии приёмки

- В Prometheus доступны гистограммы latency по всем HTTP-эндпоинтам.
- В Grafana отображаются P50 / P95 / P99 и RPS по каждому эндпоинту.
- Экспортируются бизнес-метрики (алерты, уведомления, очередь, ошибки Redis).
- Проведено нагрузочное тестирование минимум по трём сценариям.
- Результаты нагрузочных тестов зафиксированы в `docs/benchmarks.md`.
- Написаны и запущены Go-бенчмарки для критичных функций.
- (Опционально) pprof включается по переменной окружения и работает.

---

# 11. Технологический стек

- `github.com/prometheus/client_golang` (гистограммы, counter, gauge);
- Grafana (дашборды, provisioning);
- `hey` / `k6` / `vegeta` (нагрузочное тестирование);
- `testing.B` (Go-бенчмарки);
- `net/http/pprof` (опционально).

---

# 12. Взаимодействие с другими этапами

- **Этап 3 (Prometheus/Grafana)**: расширяется новыми метриками и дашбордом.
- **Этап 4 (Redis, уведомления)**: добавляются бизнес-метрики по алертам и уведомлениям.
- **Этап 5 (Context)**: все измерения учитывают таймауты и корректное завершение.
- **Этап 7 (Docker/K8s)**: нагрузочные тесты могут запускаться против контейнера.

---

# 13. Ограничения текущей версии

- Нагрузочное тестирование проводится на локальной машине; результаты зависят от окружения.
- pprof опционален и не входит в обязательные критерии приёмки.
- Полноценный APM (OpenTelemetry, Jaeger) не внедряется.
- Сравнение производительности между версиями выполняется вручную, без автоматизации в CI.
