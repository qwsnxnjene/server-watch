# Бенчмарки производительности

## Методика

Нагрузочное тестирование выполнялось локально с помощью [`hey`](https://github.com/rakyll/hey).

Общие параметры тестов:

* HTTP-сервер: `localhost:8080`
* Запросы: 10 000 на эндпоинт
* Параллельных запросов: 200
* Все запросы выполнялись последовательно отдельными запусками
* Проверялись коды ответов HTTP и распределение задержки

> Результаты являются локальным измерением для сравнения изменений в коде и конфигурации. Они не должны интерпретироваться как гарантированная нагрузка для деплоя в реальной инфраструктуре.

Все 10000 запросов к каждому эндпоинту завершились с HTTP 200.

## Анализ по эндпоинтам

### `/health`

Самый быстрый эндпоинт:

* ~34.3k RPS
* P50: 3.5 ms
* P95: 15.6 ms
* P99: 61.2 ms

Основная масса запросов выполняется за несколько миллисекунд. Более высокий P99 связан с редкими выбросами во время локального нагрузочного тестирования.

### `/metrics`

Эндпоинт отдаёт текущие системные метрики:

* ~10.3k RPS
* P50: 18.5 ms
* P95: 23.6 ms
* P99: 44.6 ms

Задержка распределена относительно узко: 95% запросов завершились быстрее ~24 ms.

### `/alerts`

Эндпоинт получения списка алертов:

* ~7.2k RPS
* P50: 22.0 ms
* P95: 62.2 ms
* P99: 78.3 ms

По сравнению с `/health` эндпоинт имеет более высокую задержку, что связано с выполнением дополнительной логики и работой с состоянием алертов.

### `/history`

Эндпоинт получения истории измерений:

* ~6.6k RPS
* P50: 22.2 ms
* P95: 71.8 ms
* P99: 126.3 ms
* Max: 192.6 ms

`/history` выполняет работу с SQLite и поэтому является одним из наиболее тяжёлых.

## Эксперимент с SQLite

Во время тестирования `/history` была воспроизведена проблема конкурентного доступа к SQLite:

```text
database is locked (SQLITE_BUSY)
```

При использовании обычного режима SQLite под высокой конкурентности процесс мог получить `SQLITE_BUSY` во время фоновой записи метрик.

В качестве экспериментов проверялись разные варианты конфигурации.

### Одно соединение

При:

```go
db.SetMaxOpenConns(1)
```

ошибка конкурентного доступа исчезала, однако все операции SQLite фактически сериализовались.

Результат для `/history`, 10000 запросов, `concurrency=200`:

* ~2.86k RPS
* P50: ~43 ms
* P95: ~195 ms
* P99: ~304 ms

Таким образом, ограничение пула до одного соединения уменьшает конкуренцию, но заметно ухудшает пропускную способность и задержку.

### Режим WAL (Write-Ahead Logging)

После включения:

```sql
PRAGMA journal_mode=WAL;
```

нагрузочные тесты `/history` при `concurrency=200` выполнялись без `SQLITE_BUSY`.

Один из повторных запусков показал:

* ~4.9k RPS
* P50: ~31.9 ms
* P95: ~92.7 ms
* P99: ~133.1 ms
* 10,000/10,000 HTTP 200

WAL оказался более подходящим вариантом для текущего сценария с конкурентными чтениями истории и периодической фоновой записью системных метрик.

## Конкурентное поведение

Для `/history` были дополнительно проведены тесты с разной конкурентностью:

| Конкурентность |          RPS |     P50 |     P95 |         P99 |
| ----------: | -----------: | ------: | ------: | ----------: |
|          50 |       ~4,473 |  9.5 ms | 24.6 ms |     33.1 ms |
|         100 |       ~4,583 | 18.7 ms | 46.5 ms |     59.4 ms |
|         200 | ~4,844–4,903 |  ~32 ms |  ~93 ms | ~119–133 ms |

При увеличении конкурентности пропускная способность начинает приближаться к плато, тогда как задержка продолжает расти.

Это указывает на приближение системы к точке насыщения для данного локального сценария нагрузки.

## Мониторинг задержки

В сервисе также реализован мониторинг с помощью Prometheus и Grafana c помощью гистограммы:

```text
http_request_duration_seconds
```

с labels:

```text
path
method
status
```

Это позволяет отслеживать:

* RPS;
* P50;
* P95;
* P99;
* задержку отдельных эндпоинтов;

Grafana используется для визуализации этих показателей.

## Interpretation

Полученные значения нельзя рассматривать как абсолютную производительность сервиса.

На результат влияют:

* CPU и RAM тестовой машины;
* файловая система и SQLite I/O;
* операционная система;
* Go runtime;
* локальная сеть;
* размер данных в SQLite;
* количество фоновых операций;
* конфигурация пула соединений SQLite;
* нагрузка на машину во время теста.

Текущие результаты показывают, что локальная версия сервиса обрабатывает несколько тысяч запросов в секунду на основных эндпоинтах при `concurrency=200`, при этом в проведённых тестах все 10,000 запросов завершались успешно.

## Воспроизводимость

Пример запуска:

```bash
hey -n 10000 -c 200 http://localhost:8080/history
```

Аналогичные тесты выполнялись для:

```bash
hey -n 10000 -c 200 http://localhost:8080/health
hey -n 10000 -c 200 http://localhost:8080/metrics
hey -n 10000 -c 200 http://localhost:8080/alerts
```

При сравнении результатов следует использовать одинаковые:

* количество запросов;
* конкурентность;
* конфигурацию SQLite;
* состояние сервиса;
* окружение.

Это позволяет использовать бенчмарк для дальнейшей оптимизации.
