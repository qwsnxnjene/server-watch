# Бенчмарки производительности

## Методика

Нагрузочное тестирование выполнялось локально с помощью [hey](https://github.com/rakyll/hey).

Основные параметры HTTP-тестов:

* сервер: `localhost:8080`;
* 10 000 запросов на эндпоинт;
* concurrency=200;
* каждый эндпоинт тестировался отдельным запуском;
* фиксировались RPS, P50, P95, P99, максимальная задержка и HTTP-статусы.

`/config` тестировался отдельно с меньшей нагрузкой, поскольку эндпоинт изменяет конфигурацию и записывает её на диск.

Go-бенчмарки выполнялись с помощью testing.B:

```bash
go test ./... -bench=. -benchmem
```

## Наблюдения

`/health` имеет минимальную внутреннюю нагрузку и показал наибольший RPS.

`/metrics`, `/alerts` и `/history` выполняют дополнительную работу с состоянием приложения и хранилищами, поэтому их задержка выше.

`/history` является одним из наиболее тяжёлых: он выполняет чтение истории из SQLite и последующую подготовку JSON-ответа.

Редкие выбросы задержек заметно влияют на P99 и Max, поэтому эти показатели следует рассматривать вместе с P50 и P95.

## SQLite

При нагрузке на `/history` была воспроизведена ошибка конкурентного доступа SQLite:

```text
database is locked (SQLITE_BUSY)
```

Были проверены два варианта конфигурации.

### Одно соединение

```go
db.SetMaxOpenConns(1)
```

Результат `/history`, 10 000 запросов, concurrency=200:

* RPS: ~2.86k;
* P50: ~43 ms;
* P95: ~195 ms;
* P99: ~304 ms.

Ошибка блокировки исчезла, но операции SQLite были сериализованы, что увеличило задержку и уменьшило пропускную способность.

### WAL (Write-Ahead Logging)

После включения:

```sql
PRAGMA journal_mode=WAL;
```

повторный тест `/history` при concurrency=200 показал:

* RPS: ~4.9k;
* P50: ~31.9 ms;
* P95: ~92.7 ms;
* P99: ~133.1 ms;
* 10 000/10 000 HTTP 200.

В проведённых тестах `SQLITE_BUSY` больше не наблюдалась.

### Влияние конкурентности

Для `/history` дополнительно сравнивалась нагрузка с разной конкурентностью:

| Конкурентно |          RPS |     P50 |     P95 |         P99 |
| ----------: | -----------: | ------: | ------: | ----------: |
|          50 |       ~4 473 |  9.5 ms | 24.6 ms |     33.1 ms |
|         100 |       ~4 583 | 18.7 ms | 46.5 ms |     59.4 ms |
|         200 | ~4 844–4 903 |  ~32 ms |  ~93 ms | ~119–133 ms |

При увеличении конкурентности пропускная способность начинает расти значительно медленнее, а задержка продолжает увеличиваться. Для данного локального сценария это указывает на приближение к точке насыщения.

> Эти результаты получены в отдельных запусках и не являются одной строго контролируемой серией. Между запусками возможны различия из-за состояния ОС, Go runtime и других фоновых факторов.

## Go-бенчмарки

| Операция                 |  Time/op | Memory/op | Allocs/op |
|--------------------------|---------:|----------:|----------:|
| Вычисление загрузки CPU  |   4.9 ns |       0 B |         0 |
| Парсинг /proc/stat       |  29.8 µs |   9.24 KB |        11 |
| JSON кодирование         |  9.41 µs |   3.12 KB |         3 |
| JSON декодирование       | 17.23 µs |   3.56 KB |         7 |
| In-memory alert state    |  23.9 ns |       0 B |         0 |
| Redis, одинаковые cond   |   611 µs |     936 B |        27 |
| Redis condition меняются |   464 µs |     824 B |        24 |
| SQLite чтение            |  15.8 µs |   2.29 KB |        53 |
| SQLite запись            |  17.5 µs |   1.30 KB |        32 |

Бенчмарки показывают разницу между стоимостью чистых вычислений, локальных операций с памятью и операциями с внешними хранилищами.

Например, вычисление загрузки CPU занимает несколько наносекунд, чтение и разбор `/proc/stat` - десятки микросекунд, а Redis-операции — сотни микросекунд в данном локальном окружении.

SQLite-бенчмарки используют in-memory базу и измеряют операции отдельно от HTTP-слоя.

## Prometheus и Grafana

Задержка HTTP измеряется гистограммой:

```text
http_request_duration_seconds
```

с labels:

```text
path
method
status
```

На основе этих данных в Grafana отслеживаются:

* RPS;
* P50;
* P95;
* P99;
* задержка отдельных эндпоинтов.

Бизнес-метрики сервиса также экспортируются через Prometheus.

## Ограничения

Бенчмарк не моделирует продакшн-инфраструктуру: нагрузка выполняется локально, без распределённого трафика и внешней задержки сети.

Кроме того, результаты отдельных запусков могут различаться. Поэтому приведённые значения следует использовать как **начальную точку для сравнения изменений в проекте**, а не как гарантированную производительность в проде.

## Воспроизводимость

HTTP:

```bash
hey -n 10000 -c 200 http://localhost:8080/history
```

Go:

```bash
make benchmark
```

Для корректного сравнения следует сохранять одинаковые параметры теста и конфигурацию приложения.
